`/Users/nikitafedorov008/DeveloperLibrary/fvm/default/packages/flutter` (Flutter stable, Dart 3.9 per

## Most important corrections

1. **Claim 5 is wrong (REFUTED).** The `errorMessage` branch of `TelemetryDisplay` is reachable. `UdpService`
   reports failures through `onError` and **returns normally** (`udp_service.dart:70-71`, `95-96`), while
   `connectToGT7` sets `_isConnected = true` after the await (`telemetry_service.dart:44-47`). A failed bind, a
   malformed IP in the panel, or a heartbeat send error therefore yields `errorMessage != null` **and**
   `isConnected == true`, the host gate at `home_page.dart:309` passes, and the screen renders
   `Error: UDP Error: …` / `Error: Heartbeat Error: …`. This also means the spec's §10 #13 is wrong, and that
   `connectToGT7`'s own `catch` is dead code.
2. **Claim 1's assertion is debug-only, not "debug and profile".** `--enable-asserts` is a debug-only compile
   option (`flutter_tools/lib/src/compile.dart:187`). Profile behaves exactly like release: silent shrink-wrap.
3. **Claim 2's overflow formula and all its numbers are wrong.** The correct expression is
   `overflow = 0.38·W − 110.75` (the spec double-counts the tick tip on top of the arc's half-stroke):
   +14.6 px on a 390 px phone (not +22), +59.5 px at 1000 px (not +67), +143.1 px at 1440 px (not +151), and the
   45°/135° ends land at y ≈ 306, i.e. +66 px below the box (not ≈325 / +85). "Nothing clips" is also wrong —
   `SingleChildScrollView` defaults to `Clip.hardEdge`.
4. **Claim 4: two numbers are wrong.** A major tick step is **90 km/h** (not 45), and **12** of the 15 speed
   labels fall between ticks (not 14) — the spec's own list of aligned labels (0, 360, 540) contradicts its count.
5. **Claim 8f is not reachable.** auto_route's `pageView` shell keeps every tab alive (`KeepAliveTab` +
   `maintainState` defaulting to true), so the telemetry widget is never disposed and `initialize()` is
   dispatched once; and even with two timers the 10 ms de-dup would hold the accepted rate at ~62.5 Hz, so
   "double sample rate" is not achievable. The unsafe assignment and the never-stopped poll timer are still real
   defects.
6. **Claim 9's enumeration is off by one.** The "63 unrendered" total is right (86 − 23) but the table lists only
   62 rows; `packetId` is missing. "86 parsed" should be "86 declared (76 packet reads + 10 derived)".
7. **Claim 10 needs two caveats.** A **brake** numeric readout exists (the chip at `telemetry_display.dart:271`);
   and "no on-screen controls" is true only for this screen — connect/demo controls live in
   `telemetry_panel.dart` on the Home tab.

## What cannot be settled by reading code

* Actual rendered pixel values (the spec's own caveat) — including whether a NaN path draws nothing or an engine
  warning, and whether overdraw is visually noticed.
* Whether a `RawDatagramSocket.bind`/heartbeat error actually occurs on a given run (the state that makes claim 5's
  branch visible is code-reachable, but the trigger is a runtime failure).
* Any conclusion that needs a device: the debug red screen, and the exact real-GT7 packet cadence that decides how
  many duplicate samples the 62.5 Hz poll produces. Settling those needs `flutter run` / a device, which the
  sandbox blocks.
